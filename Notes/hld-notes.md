## [2026-05-25] H10 · Rate Limiter · **Cloudflare** · Stripe · Anthropic

- Sliding window counter vs token bucket — why the window approximation wins at scale
- Edge-local vs centralized Redis counters — the latency/accuracy trade-off

### Problem (as asked)

> "Design a distributed rate limiter. 10M users, each with their own quotas (e.g. 100 req/min). Decisions must be made in under 5ms p99. Quotas must hold even under burst traffic across multiple API servers."

**Clarifying questions to ask back before drawing anything:**

1. Are quotas uniform (100 req/min for all) or per-tier (free=60, pro=1000, enterprise=custom)?
2. What's the fail-open/fail-closed policy when the limiter's backing store is unreachable?
3. Is this API-level (HTTP) or transport-level (L4/TCP)? Determines where the enforcement point sits.
4. Multi-region deployment? If yes, is the quota global or per-region?
5. Do we need a `Retry-After` header with accurate remaining-time, or just `429`?

### Back-of-envelope

```
Users:          10M active
Quota:          100 req/min per user (baseline)
Peak QPS:       assume 20% of users active in peak hour
                10M × 0.2 × 100 / 60 = ~3.3M QPS at peak
                (but most requests are ALLOWED; only ~1% hit the limit)

State per user: token-bucket = 2 integers (tokens, last_refill_ts) = ~16B
                sliding-window-counter = 2 integers (prev_count, curr_count) = ~16B

Total state:    10M × 16B = 160 MB  ← fits in ONE Redis instance's memory
                Even with overhead (key, hash slot, etc): ~1 GB total

Redis ops:      Each rate-limit check = 1 EVALSHA (atomic Lua script)
                3.3M QPS → ~3.3M Redis ops/sec
                Single Redis: ~100k ops/sec → need ~33 shards
                Redis Cluster with 40 shards handles this comfortably

Latency budget: 5ms p99 for the decision
                Intra-DC Redis RTT: ~0.5ms p50, ~2ms p99
                Lua script execution: ~0.1ms
                Total: ~2ms p99 — within budget with margin

Bandwidth:      3.3M QPS × ~100B per request/response = ~330 MB/s
                Standard 10 Gbps NIC handles this
```

### Functional / Non-functional requirements

| Functional | Non-functional |
|---|---|
| Check if request is within quota → allow/deny | p99 decision latency < 5ms |
| Per-user quotas (configurable per tier) | 99.99% availability (fail-open preferred over hard-down) |
| Return `429 Too Many Requests` + `Retry-After` header | Accuracy: ±5% overshoot acceptable (not billing) |
| Rate-limit headers on every response (`X-RateLimit-Remaining`) | Horizontally scalable to 10M+ users |

### API contract

```
-- Internal middleware interface (not user-facing API)
RATE_CHECK(user_id, endpoint, quota_config) → { allowed: bool, remaining: int, retry_after_ms: int }

-- Response headers on every API response:
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 73
X-RateLimit-Reset: 1716400060        # Unix epoch when window resets

-- On rejection:
HTTP 429 Too Many Requests
Retry-After: 12                      # seconds until next window
```

Notes: the rate limiter is middleware, not an external API. It sits in the request path between the load balancer and the application handler.

### Data model

```
Redis key schema (sliding window counter):
  Key:    rl:{user_id}:{endpoint}:{window_minute}
  Value:  integer (request count in this window)
  TTL:    120s (2× window size — need current + previous window)

Example:
  rl:usr_abc123:api/chat:27609321  →  47
  rl:usr_abc123:api/chat:27609320  →  91   (previous minute)

Quota config (in application config / DB, NOT in Redis):
  user_tier    varchar     PK
  endpoint     varchar     PK
  max_requests int
  window_sec   int
  burst_mult   float       -- e.g., 1.5× for token bucket burst allowance
```

Access patterns: every request does one atomic `INCR + GET` on the current-window key + one `GET` on the previous-window key. Both are O(1) Redis operations on the same hash slot (same `{user_id}` hash tag).

### Architecture

```
        Incoming request (3.3M QPS peak)
                    │
                    ▼
          ┌──────────────────┐
          │   Edge / LB      │
          │  (no rate logic)  │
          └────────┬─────────┘
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
   ┌──────────┐        ┌──────────┐
   │ API pod  │  ...   │ API pod  │    (~500 pods)
   │ (Go/Rust)│        │          │
   └─────┬────┘        └─────┬────┘
         │  EVALSHA (Lua)     │
         │  ~0.5ms p50        │
         ▼                    ▼
   ┌─────────────────────────────────┐
   │   Redis Cluster (40 shards)    │   ← 160 MB user state
   │   hash-tag: {user_id}          │     fits comfortably
   │   each shard: ~80k ops/sec     │
   └─────────────────────────────────┘

   On ALLOW → request continues to application handler
   On DENY  → 429 returned immediately (no app handler invoked)
```

NFR landing points:
- **p99 < 5ms** → intra-DC Redis RTT ~2ms p99 + Lua ~0.1ms = ~2.1ms. Margin for GC/network jitter.
- **99.99% availability** → fail-open policy: if Redis is unreachable, allow the request (log for offline reconciliation). Availability of the *API* is not gated on the limiter.
- **Accuracy** → sliding window counter gives ±5% approximation vs true sliding window. Acceptable for rate limiting (not billing).

### Deep dive 1: Sliding window counter vs token bucket vs fixed window

**1. Why does this mechanism exist?**

You need to count "how many requests has this user made in the last N seconds" and compare against a threshold. The naive approach — fixed window (reset counter every minute) — has a well-known bug: a user can send 100 requests at second 59 and 100 more at second 61, getting 200 requests in a 2-second span while never exceeding the per-minute limit. The window boundary is an exploitable seam.

Four algorithms address this differently:

| Algorithm | State per user | Time complexity | Burst-boundary behavior |
|---|---|---|---|
| Fixed window | 1 counter + reset_ts | O(1) | Broken — 2× burst at boundary |
| Sliding window log | Sorted set of all timestamps | O(N) per check | Perfect — exact count |
| **Sliding window counter** | 2 counters (prev + curr window) | O(1) | Approximate — ±5% error |
| Token bucket | 2 values (tokens + last_refill) | O(1) | Smooth — allows configured burst |

The **sliding window log** is the theoretically correct answer but stores every request timestamp. At 100 req/min × 10M users, that's 1 billion sorted-set entries at peak — ~60 GB of Redis memory for timestamps alone. The storage cost kills it.

The **token bucket** is the classic textbook answer. It allows a configured burst (bucket capacity) and refills at a steady rate. It's elegant for single-server rate limiting but has a subtle distributed problem: the refill calculation (`tokens += (now - last_refill) × rate`) requires an atomic read-modify-write of *two* fields, which is slightly more complex in a Lua script than a simple counter increment.

The **sliding window counter** is the boring-correct answer for distributed systems at scale. It uses two fixed-window counters and interpolates:

```
effective_count = prev_window_count × (1 - elapsed_fraction) + curr_window_count

Example: window = 60s, we're 15s into the current minute
  prev_window_count = 80
  curr_window_count = 30
  elapsed_fraction  = 15/60 = 0.25
  effective_count   = 80 × 0.75 + 30 = 90

  If quota = 100 → 10 remaining → ALLOW
```

**2. Walk it concretely.**

User `usr_abc123` has a 100 req/min quota. Current Unix minute = `27609321` (i.e., `floor(unix_ts / 60)`). We're 40 seconds into this minute.

```
Redis state before request:
  rl:{usr_abc123}:api:27609321  =  62    (current window, 62 requests so far)
  rl:{usr_abc123}:api:27609320  =  88    (previous window, 88 total)

Lua script executes atomically:
  1. curr_key  = "rl:{usr_abc123}:api:27609321"
  2. prev_key  = "rl:{usr_abc123}:api:27609320"
  3. curr_count = GET curr_key           → 62
  4. prev_count = GET prev_key           → 88
  5. elapsed    = unix_ts % 60           → 40
  6. weight     = 1 - (40 / 60)          → 0.333
  7. effective  = 88 × 0.333 + 62        → 91.3
  8. if effective < 100:
       INCR curr_key                     → 63
       if NEW key: EXPIRE curr_key 120   (2× window for overlap)
       return {allowed: true, remaining: 8}
     else:
       return {allowed: false, retry_after: 60 - 40 = 20s}

Redis state after:
  rl:{usr_abc123}:api:27609321  =  63    (incremented)
  rl:{usr_abc123}:api:27609320  =  88    (untouched, TTL ticking)
```

At the window boundary (minute rolls to `27609322`):
- `27609321` becomes the "previous" window (still in Redis, TTL has ~60s left)
- `27609322` starts at 0
- `27609320` expires via TTL — no explicit cleanup needed

The TTL-based cleanup is the key insight: **no background job, no GC, no scan**. Redis evicts stale windows automatically. This is why sliding window counter scales to millions of users with minimal operational overhead.

**3. The cost you're accepting.**

| Property gained | Cost paid |
|---|---|
| O(1) state per user (2 integers vs N timestamps) | ±5% accuracy — can overshoot quota by ~5 requests at 100 req/min |
| No sorted-set scans — pure GET/INCR | Approximation assumes uniform request distribution within a window |
| TTL-based cleanup — no background GC | If requests cluster at window boundaries, error can reach ~10% |
| Simple Lua script (6 lines) — easy to audit | Cannot give exact `remaining` count — it's an estimate |

The ±5% error bound was proven by Cloudflare's engineering team in their 2017 blog post. For a rate limiter (not a billing system), 5% overshoot is operationally irrelevant — the purpose is preventing abuse, not precise metering.

**4. Failure modes the interviewer will drill into.**

| Failure | What goes wrong | Mitigation |
|---|---|---|
| Clock skew between API pods | Different pods compute different `elapsed_fraction` for the same instant → inconsistent allow/deny | Use Redis server time (`TIME` command) in the Lua script, not client time. All decisions based on one clock. |
| Hot user (10k req/sec from one user) | All requests hash to one Redis shard → that shard saturates | Replicate hot-user keys across N shards with read-from-any; or local per-pod token bucket as L1 with Redis as L2 |
| Redis shard failure | Rate limit state for ~250k users (10M / 40 shards) lost | Fail-open: allow requests, log them, reconcile when shard recovers. Alert on sustained failure. |
| Lua script bug (e.g., TTL not set) | Keys accumulate forever → Redis OOM | `EXPIRE` is idempotent; set it on every INCR, not just on creation. Monitor `dbsize` and `used_memory`. |
| Burst of new users (10k signups/sec) | Sudden spike in new Redis keys → memory pressure | Pre-set `maxmemory-policy allkeys-lru`; rate-limit keys are small (16B value) — 10k new users = ~160 KB. |

**5. How to derive it in an interview from first principles.**

1. State the constraint: count requests per user in a rolling time window, O(1) per check, distributed across N servers.
2. Fixed window is the simplest counter — but the boundary exploit means a user can 2× burst. Rejected.
3. Exact sliding window (sorted set of timestamps) fixes the boundary but costs O(N) storage and O(log N) per check. At 100 req/min × 10M users, that's billions of entries. Rejected at scale.
4. Observation: you don't need *exact* count. ±5% is fine for abuse prevention.
5. Key insight: if you know the *total count* of the previous fixed window and the *partial count* of the current window, you can *interpolate* the sliding window count using the time elapsed in the current window.
6. This gives you O(1) state (two integers) and O(1) check (one multiply + one add). The approximation error is bounded by how non-uniform the request distribution is within a window.
7. You've derived the sliding window counter without citing the Cloudflare blog — but they proved the error bound empirically at millions of domains.

**6. Where this shows up in production.**

- **Cloudflare**: sliding window counter at their edge. Their 2017 engineering blog reported handling rate limiting across **millions of domains** with this exact algorithm. The approximation formula `prev × (1 - overlap) + curr` is quoted verbatim. They chose it over token bucket specifically because the two-counter approach maps cleanly to Redis atomic operations.
- **Stripe**: token bucket for their API rate limiter (documented in their "Scaling your API with rate limiters" blog). They chose token bucket over sliding window because Stripe's quotas need burst allowance — a merchant processing a batch of charges should be allowed to burst up to 2× rate briefly. The `burst_capacity` parameter in token bucket maps directly to this business requirement.
- **Anthropic**: per-model, per-tier rate limiting for the Claude API. Quotas differ by model (Haiku vs Opus) and by tier (free vs scale). The rate limiter must make decisions in <5ms because it sits in the critical path before the inference queue. Uses a hybrid approach: edge-local approximate check + centralized Redis for authoritative state.
- **GitHub**: per-user and per-IP rate limiting on their REST and GraphQL APIs. 5,000 req/hour for authenticated users, 60 req/hour for unauthenticated. They expose `X-RateLimit-*` headers on every response — the sliding window counter's approximate `remaining` count is "good enough" for the header.

### Deep dive 2: Edge-local enforcement vs centralized Redis counters

**1. Why does this mechanism exist?**

The 5ms p99 latency budget creates a tension: **accuracy requires centralization** (one Redis cluster is the source of truth for all counters), but **latency requires locality** (every network hop adds ~0.5ms intra-DC, ~50ms cross-DC).

With 500 API pods and 3.3M QPS, a single centralized Redis cluster works within a single datacenter (intra-DC RTT ~0.5ms). But when the API spans multiple regions (us-east, eu-west, ap-south), you face a choice:

```
Option A: Global Redis (one region)
  us-east pod → us-east Redis: 0.5ms  ✅
  eu-west pod → us-east Redis: 80ms   ❌ (blows 5ms budget)

Option B: Per-region Redis (independent)
  eu-west pod → eu-west Redis: 0.5ms  ✅ for latency
  But: user quota is now per-region, not global
  User sends 100 req to us-east + 100 req to eu-west = 200 total  ❌

Option C: Hybrid — edge-local approximate check + async sync
  Each pod keeps a local counter (fast, approximate)
  Syncs to regional Redis periodically (accurate, slightly delayed)
  ✅ latency, ⚠️ accuracy (bounded overshoot)
```

The choice depends on the product's tolerance for overshoot. For most API rate limiters, Option B (per-region Redis with per-region quota that sums to global) or a simple single-region deployment (Option A) is sufficient. Option C is for extreme latency sensitivity.

**2. Walk it concretely.**

**Single-region deployment (the common case, and what we'll build first):**

```
500 API pods in us-east, 40-shard Redis Cluster in us-east

Request arrives at Pod 37:
  1. Pod 37 extracts user_id from auth token     (~0.1ms)
  2. Pod 37 computes Redis hash slot:
     hash_slot = CRC16("{usr_abc123}") % 16384    → slot 7291
     slot 7291 lives on shard 12
  3. Pod 37 sends EVALSHA to shard 12              (~0.5ms network)
  4. Lua script runs sliding-window-counter        (~0.1ms)
  5. Result returns to Pod 37                      (~0.5ms network)
  Total: ~1.2ms

Pod 37 and Pod 412 both process requests from usr_abc123 simultaneously:
  Both talk to shard 12 (same hash slot)
  Redis is single-threaded per shard → requests are serialized
  No race condition possible — the Lua script is atomic
  Order: Pod 37's INCR executes first, Pod 412 sees the incremented value
```

**Multi-region with per-region quotas:**

```
Global quota: 100 req/min
Regions: us-east (60%), eu-west (30%), ap-south (10%)
Regional allocation: us-east=60, eu-west=30, ap-south=10

Each region has its own Redis cluster.
us-east Redis enforces 60 req/min for usr_abc123.
eu-west Redis enforces 30 req/min for usr_abc123.

User sends 60 req to us-east → allowed (hits limit)
User sends 30 req to eu-west → allowed (hits limit)
Total: 90 — under global quota ✅

Edge case: user sends ALL 100 req to eu-west → only 30 allowed, 70 rejected
           even though globally they have 100 quota.
           This is the cost: regional allocation creates artificial local limits.
```

**Hybrid with edge-local counters (for <1ms decision latency):**

```
Each API pod maintains a local in-memory counter:
  local_count[usr_abc123] = 0
  local_quota = global_quota / num_pods = 100 / 500 = 0.2 req/min per pod

Problem: 0.2 req/min is not a usable quota — any single request exceeds it.

Better approach — local token bucket with periodic Redis sync:

  Pod 37 local state:
    tokens = 5          (borrowed from Redis)
    last_sync = T-2s    (syncs every 3 seconds)

  Request arrives:
    tokens > 0 → ALLOW, tokens-- (0ms, pure local)

  Every 3 seconds:
    Pod 37 → Redis: "I used 12 tokens since last sync, give me 15 more"
    Redis:  global_remaining = 100 - 12 - (other pods' usage) = 41
            grant = min(15, 41 / active_pods) = 15
    Pod 37: tokens = 15

  Trade-off: up to 3s of uncoordinated usage → global quota can overshoot
             by (num_active_pods × local_bucket_size)
             = 50 active pods × 5 tokens = 250 requests over quota
             At 100 req/min quota → 3.5× overshoot in worst case
```

The hybrid approach trades **accuracy for latency**. For most API rate limiters, the centralized Redis approach (single-region, 1-2ms) is sufficient. The hybrid is reserved for edge-compute scenarios (Cloudflare Workers, CDN-level enforcement) where even 0.5ms to Redis is too much.

**3. The cost you're accepting.**

| Approach | Latency | Accuracy | Operational complexity | Failure mode |
|---|---|---|---|---|
| **Centralized Redis (single-region)** | ~1-2ms intra-DC | Exact (serialized) | Low — one cluster | Redis down = no limiting |
| Per-region Redis (split quota) | ~1-2ms intra-DC | Exact per-region, imprecise globally | Medium — N clusters | Regional quota imbalance |
| Hybrid edge-local + Redis | <0.1ms local decision | ±250% overshoot worst case | High — local state + sync protocol | Pod crash loses local count |
| Pure local (no central state) | <0.1ms | Useless at low per-pod quota | Low per-pod | No global enforcement |

**4. Failure modes the interviewer will drill into.**

| Failure | What goes wrong | Mitigation |
|---|---|---|
| Redis cluster fully down (all shards) | No rate-limit state → either block all requests (fail-closed) or allow all (fail-open) | Fail-open with local fallback: each pod enforces a conservative local limit (quota / expected_pods) while Redis is down. Log all requests for post-recovery reconciliation. |
| Network partition between pods and Redis | Some pods can reach Redis, others can't → inconsistent enforcement | Pods that can't reach Redis fail-open with local bucket; monitoring alerts on partition; once healed, Redis state is authoritative (local counts discarded). |
| Redis shard hot-spot (celebrity user) | 10k req/sec from one user → one shard at 10k ops/sec (exceeds ~100k budget) | Detect hot keys via `SLOWLOG`; replicate that user's key to 3 shards with read-from-any; or short-circuit deny at the pod level once the user is flagged. |
| Quota config change mid-window | User's quota changes from 100 to 50 while they've already used 80 → should they be limited immediately? | Apply new quota on next window boundary, not mid-window. The current window's counter is already in flight; changing the threshold mid-stream creates inconsistent `remaining` headers. |
| Pod restart during hybrid sync | Pod had 12 unsync'd request counts → lost on crash → user gets 12 "free" requests | Accept: 12 requests at 100 req/min quota is a 12% overshoot for one window. Not worth persisting local state to disk for this. |

**5. How to derive it in an interview from first principles.**

1. State the constraint: 5ms p99 decision latency, 10M users, distributed across N API servers.
2. The decision must be consistent across servers: user sends requests to any pod, total must not exceed quota.
3. Consistency across servers → shared state. Options: shared database, shared cache, gossip protocol.
4. Database: too slow (5-15ms per query, already at budget). Gossip: convergence time too slow for per-request decisions.
5. Redis: in-memory, single-threaded (no locking), Lua scripts for atomicity, intra-DC RTT ~0.5ms. **Fits the latency budget.**
6. Single Redis cluster in one region handles single-region deployment. For multi-region: split quota proportionally per region.
7. For sub-millisecond requirements (edge compute): add local token bucket per pod, sync to Redis every N seconds. Trade: accuracy degrades proportionally to sync interval × pod count.
8. Fail-open policy: if Redis is down, the API should still serve requests. Rate limiting is a *protection mechanism*, not a *correctness requirement*. Blocking all API traffic because the limiter is down is worse than allowing some over-quota requests.

**6. Where this shows up in production.**

- **Cloudflare**: edge-enforced rate limiting across 285+ POPs. Each POP has local counters with periodic sync to regional aggregation points. They accept ~10% overshoot at the edge in exchange for <1ms enforcement latency. Their 2017 blog explicitly discusses the centralized-vs-edge trade-off and why edge wins for their use case (CDN-level enforcement where every millisecond of added latency is a customer-visible regression).
- **Stripe**: centralized Redis-backed rate limiter. Single-region deployment (us-east primary). Their documented architecture uses token bucket with Redis as the backing store. They specifically chose centralized over distributed because billing accuracy matters more than sub-millisecond latency — a financial API can tolerate 2ms rate-limit overhead; it cannot tolerate 2× overshoot on a metered endpoint.
- **AWS API Gateway**: per-region token bucket with configurable burst. Default: 10,000 req/sec steady-state, 5,000 burst capacity. Each region enforces independently — no cross-region quota coordination. A customer with 10k req/sec global can get 10k in us-east AND 10k in eu-west (20k total) if they spread traffic. AWS documents this explicitly as a known behavior, not a bug.
- **Envoy proxy (Lyft/Google)**: local rate limiting (per-pod) + global rate limiting (centralized gRPC service). The `envoy.filters.http.local_ratelimit` filter handles per-connection limits locally. The `envoy.filters.http.ratelimit` filter calls an external rate-limit service (Redis-backed). Both can be composed: local filter short-circuits obvious abuse, global filter enforces accurate quotas.

### Bottlenecks + scaling levers

| Scale point | First bottleneck | Lever |
|---|---|---|
| 10× users (100M) | Redis memory: 100M × 16B = 1.6 GB — still fits easily | No action needed; Redis handles it |
| 10× QPS (33M) | Redis cluster throughput: 33M ops/sec needs ~330 shards | Add shards; or add per-pod L1 cache (local token bucket) to reduce Redis load by ~80% |
| Multi-region (3 regions) | Cross-region Redis latency blows 5ms budget | Per-region Redis with proportional quota split |
| 100× users (1B) | Redis key count: 1B keys × ~100B per key = ~100 GB | Shard across multiple Redis clusters; or move to a tiered approach (hot users in Redis, cold users in local-only) |

### Trade-off matrix

| Option | Latency | Accuracy | Cost | Complexity | Failure mode |
|---|---|---|---|---|---|
| Fixed window counter | ✅ <1ms | ❌ 2× burst at boundary | ✅ minimal | ✅ trivial | ⚠️ exploitable |
| Sliding window log (sorted set) | ✅ <2ms | ✅ exact | ❌ 60 GB at scale | ❌ O(N) cleanup | ⚠️ OOM risk |
| **Sliding window counter (chosen)** | ✅ <2ms | ⚠️ ±5% | ✅ 1 GB total | ✅ 6-line Lua | ⚠️ fail-open |
| Token bucket (single-server) | ✅ <1ms | ✅ exact | ✅ minimal | ✅ simple | ⚠️ no distribution |
| Token bucket (Redis-backed) | ✅ <2ms | ✅ exact | ✅ minimal | ⚠️ CAS loop | ⚠️ fail-open |

Chose **sliding window counter** for the combination of O(1) state, O(1) check, no CAS retry loop, and proven-at-scale (Cloudflare). Token bucket is the runner-up — equally valid; the interview signal is explaining *why* you chose one over the other, not which one.

### Common follow-ups

1. **What if Redis is temporarily unavailable?** — Fail-open: allow all requests, enforce a conservative local per-pod limit (quota / expected_pod_count), and log every request for post-recovery reconciliation. Alert on Redis downtime. The API must not go down because the rate limiter is down — the limiter is a guardrail, not a gate.
2. **How do you handle 100 requests from one user hitting 50 different API servers simultaneously?** — All 50 requests hash to the same Redis shard (hash tag `{user_id}`). Redis is single-threaded → the 50 `EVALSHA` calls are serialized. Each sees the incremented counter from the prior call. Worst case: all 50 arrive in 1ms → Redis processes them in ~5ms serial → last few see the counter at 100 and get denied. No race condition.
3. **Can you do it without any centralized state?** — Yes, but accuracy degrades. Each pod maintains a local token bucket with `quota / num_pods` allocation. At 100 req/min across 500 pods = 0.2 req/min per pod — any single request exceeds the local quota. Requires periodic token redistribution protocol (gossip or coordinator). Operationally painful; only justified if sub-0.5ms latency is a hard requirement.
4. **How do you handle different quotas per endpoint?** — Separate Redis key per `(user_id, endpoint)` pair. The Lua script takes `endpoint` as a parameter and computes a different key. Quota configs live in application config (not Redis). Key count increases by the number of distinct endpoints (~10-20 typically) — still O(1) per user.
5. **How do you rate-limit by IP instead of user (for unauthenticated traffic)?** — Same mechanism, different key: `rl:{ip}:{endpoint}:{window}`. Risk: NAT/proxy means thousands of users share one IP. Mitigation: higher per-IP quota (1000 req/min) + fingerprinting (User-Agent, TLS fingerprint) for finer-grained limiting. Cloudflare uses JA3 TLS fingerprinting for this.

### What top-tier looks for

- **Mid-tier says**: "Use a token bucket. Store it in Redis. Return 429 when the bucket is empty."
- **Staff-tier says**: "Token bucket and sliding window counter are both valid — the choice depends on whether you need burst allowance (token bucket) or simpler distributed implementation (sliding window counter). I'd start with sliding window counter because the two-counter interpolation maps to two atomic Redis operations with no CAS retry loop. The real design question isn't the algorithm — it's the **fail-open policy**: when Redis is down, do you block all API traffic or allow all of it? For a rate limiter protecting an API, fail-open is almost always correct — the limiter is a guardrail, not a correctness mechanism. The exception is financial APIs where overshoot has dollar cost."

Why the difference: mid-tier names the algorithm. Staff-tier names the **operational decision** (fail-open vs fail-closed) that determines the system's behavior during the failure mode that actually matters (Redis outage), and connects it to the business context (guardrail vs billing).

### Diagnostic questions (self-quiz)

1. **Why not fixed-window counters?** — wrong: "They're too simple." Right: the window-boundary exploit lets users 2× burst by straddling the reset. 100 requests at :59 + 100 at :01 = 200 in 2 seconds while never exceeding the per-minute limit.
2. **Why is fail-open the right default?** — wrong: "We don't want to block users." Right: the rate limiter is a *protection mechanism*; its failure should not cascade into API unavailability. Blocking all traffic because the limiter is down is a self-inflicted outage — worse than allowing some over-quota requests.
3. **How does the sliding window counter handle clock skew between pods?** — wrong: "Use NTP." Right: don't use client time at all. The Lua script runs on the Redis server and uses Redis's `TIME` command. All decisions are based on one clock — the Redis server's. NTP only needs to keep the API pods' clocks close enough for log correlation, not for rate-limit correctness.
4. **Why hash-tag `{user_id}` in the Redis key?** — wrong: "For organization." Right: Redis Cluster routes keys to shards by hashing the content inside `{}`. `{user_id}` ensures both the current-window and previous-window keys land on the **same shard**, so the Lua script can atomically read both in a single `EVALSHA` (multi-key Lua requires all keys on the same shard).
5. **At what point does centralized Redis stop working?** — wrong: "When you have too many users." Right: when you go multi-region and cross-DC latency (50-80ms) blows the 5ms budget. The solution is per-region Redis with proportional quota split, not a bigger Redis cluster.

### Data model

### Deep dive 1: ID generation — base62 counter vs hash vs Snowflake

**1. Why does this mechanism exist?**

The system must mint a unique short ID for each new URL. Three properties matter:
**(a)** uniqueness — no two URLs share an ID,
**(b)** URL-safety — ID survives copy-paste through Slack, SMS, QR codes (no `+`, `/`, `?`, `#`),
**(c)** compactness — shortening is literally the product.

A naive auto-incrementing integer satisfies (a) and (b) but gives you `srt.ly/100000000` — 9 digits — and **defeats (c)**. You need a denser encoding of the integer space.

The decision space:

| Approach | Idea |
|---|---|
| Hash of URL | `base62(MD5(url)[:7])` — deterministic, idempotent on same URL |
| Distributed counter | A monotonic integer, encoded base62 |
| Snowflake | 64-bit ID = timestamp + machine_id + sequence; encoded base62 |

The constraint that decides the answer: **365B URLs total over 10 years.** At 7-char base62 (62⁷ = 3.5 × 10¹² slots), you have ~10× headroom — fine. At 6-char base62 (62⁶ = 5.7 × 10¹⁰ slots), you'd burn 365B / 57B = ~6.4× the space; collision-retry under hash would make this catastrophic. **So minimum ID width = 7 chars; counter approach uses the slot space densely; hash approach wastes ~60% of it to avoid collisions.**

**2. Walk it concretely.**

**Counter approach (sharded + pre-allocation).** Shard 0 has `counter_state.next_id = 14_276_804_201`. Two concurrent shortens land at two API pods:

```
Pod A startup:
  UPDATE counter_state SET next_id = next_id + 1000 WHERE shard_id = 0 RETURNING next_id - 1000;
  -- returns 14_276_804_201; Pod A now owns IDs 14_276_804_201 .. 14_276_805_200
  -- Pod A serves 1000 shortens locally with NO further DB round-trips for ID allocation.

POST /shorten   url=https://example.com/path-1   (lands on Pod A)
  → next local ID = 14_276_804_201
  → base62(14_276_804_201) = "vG3a8N0"           (7 chars)
  → INSERT INTO links (id, long_url, shard_id) VALUES ('vG3a8N0', ..., 0);
  → 201 { short_url: "srt.ly/vG3a8N0" }

POST /shorten   url=https://example.com/path-2   (lands on Pod B, also shard 0)
  → Pod B has its own block (14_276_805_201 .. 14_276_806_200)
  → next local ID = 14_276_805_201 → base62 = "vG3aFa1"
  → No collision possible — Pod A and Pod B own disjoint ranges.
```

The atomic `UPDATE … RETURNING` is the only coordination cost; with 32 shards × 1000-ID blocks, the counter row sees ~1 update/sec per shard at peak — Postgres handles it in single-digit ms with no contention.

**Snowflake approach (distributed).**

```
64-bit ID layout:  | 41 bits timestamp_ms | 10 bits machine_id | 12 bits seq |
                          (until 2079)            (1024 nodes)    (4096 IDs/ms/node)

machine_id = 7;  timestamp_ms = 1_716_400_000_000;  seq = 0
ID = (1_716_400_000_000 << 22) | (7 << 12) | 0
   = 7_198_787_829_563_817_984
base62(ID) = "1A9bF3kP"     -- 11 chars (the 64-bit integer)
```

Two problems immediately:
- **ID width is ~11 chars in base62** — 4 chars longer than counter approach for the same uniqueness guarantee. For a service whose product is "short URL," that's a 60% regression on the headline metric.
- **Clock skew** between machines breaks uniqueness if two nodes share a `machine_id` by mistake or if NTP slips backward.

**3. The cost you're accepting.**

| Approach | Gains | Pays |
|---|---|---|
| **Counter (sharded + pre-alloc)** | Tightest ID width (7 chars); no clock dep; dense slot use | Lost IDs on pod crash (mitigated by 10× headroom); per-shard SPoF (mitigated by PG replication) |
| **Snowflake** | Fully distributed; no DB round-trip per ID; time-sortable | ~60% wider IDs; clock-skew failure mode; ID leaks creation timestamp (privacy/abuse) |
| **Hash** | Idempotent on URL (free dedup); fully distributed; trivial code | Collisions are guaranteed at scale (birthday paradox); retry loop = variable insert latency |

The "ID is sortable by time" property of Snowflake matters occasionally (range queries by creation time) but here `created_at` is already a separate column — no need for the ID to encode time.

**4. Failure modes the interviewer will drill into.**

| Failure | What goes wrong | Mitigation |
|---|---|---|
| Counter row hot-spot (writes funnel into one Postgres tuple → row lock contention) | UPDATE latency spikes; tail latency on shortens | Pre-allocate blocks of 1k IDs per pod (cuts contention 1000×); or use `SEQUENCE … CACHE 1000` |
| Pod crashes with 700 reserved IDs unused | Those 700 IDs are wasted | Accept: ID space has 10× headroom; alternatively, persist block reservation and recover on restart |
| Two pods claim the same `machine_id` (Snowflake) | Duplicate IDs across pods → INSERT conflict OR silent overwrite | Lease `machine_id` from ZooKeeper/etcd at startup; reject duplicates with TTL renewal |
| NTP slip — clock goes backward in Snowflake | Same `(timestamp, seq)` issued twice → duplicate ID | Block ID generation until wall clock passes `last_issued_timestamp`; alarm if drift > 1s |
| Hash collision under load | Two URLs get same short ID → second INSERT fails on unique constraint OR overwrites | Check-then-insert with unique constraint; on conflict, salt the hash and retry — adds variable latency to write path |

**5. How to derive it in an interview from first principles.**

1. State the constraint: 365B unique IDs over 10 years; URL-safe; compact.
2. Encoding: base62 is URL-safe (`a-zA-Z0-9` — no escaping per RFC 3986) and dense. Minimum width: 62⁷ = 3.5T slots > 365B. So width = **7 chars**.
3. Need to assign 365B unique values to URLs over time. Options for assignment:
4. **Hash** — function of input, no coordination. Rejected: birthday paradox forces retry-on-collision; insert latency becomes unbounded under load.
5. **Single monotonic counter** — perfect uniqueness, dense slot use. Rejected: one row owns the global counter — not horizontally scalable.
6. **Sharded counter** — counter per shard; each pod pre-allocates a block. Coordination cost = one UPDATE per block (~1k IDs). Slot use dense; no clock dep. **Chosen.**
7. Mention Snowflake as the alternative the interviewer might push: distributed, no DB, but ID width regresses to ~11 chars. Not worth the trade for a product whose name is "short."

**6. Where this shows up in production.**

- **bit.ly**: counter-based ID generation, sharded by ID range. 2009 engineering blog described their "shard router" mapping ID prefix → Cassandra cluster. Migrated to sharded counters circa 2012.
- **Twitter Snowflake (2010)**: 64-bit ID = 41 bits timestamp + 10 bits worker + 12 bits sequence. ~600 IDs/ms per worker. Powers tweet IDs, media IDs. Open-sourced; the canonical reference for "distributed time-based ID."
- **Stripe**: prefixed-time-sortable IDs (`cus_1234abcd`, `ch_5xyz`). 9-char base62 random suffix with collision retry; prefix is the resource type. Chose human-readability over slot density.
- **YouTube**: 11-char base64url IDs; pseudo-random with collision check. ~64¹¹ ≈ 7 × 10¹⁹ slots — vastly oversized; they trade slot waste for **unpredictability** (don't want IDs to leak upload order).
- **Discord**: Snowflake variant — worker ID = process counter, not machine ID; 4096 IDs/ms/process gives them ~4M new IDs/sec/process. Trade: more workers per host, more lease-coordination cost.

### Deep dive 2: Cache topology — 3-tier (CDN edge + Redis L2 + sharded DB)

**1. Why does this mechanism exist?**

The p99 budget is **100ms over network**. Network RTT alone is 30-80ms for a cross-region request, leaving <70ms for everything else (TLS handshake, processing, DB I/O). A DB round-trip is 5-15ms intra-DC + the same RTT back to user; you cannot hit the DB on every redirect and stay under 100ms p99.

The mechanism: a **multi-tier cache where the vast majority of requests terminate close to the user**, with the DB as a cold-path last resort.

| Tier | Where | Latency contribution | Traffic share (steady-state) |
|---|---|---|---|
| CDN edge | 200+ POPs globally | 5-20ms (geo) | 95% |
| Redis L2 | Same region as origin | ~1ms intra-DC | 4% (post-CDN-miss) |
| DB shards | Same region as origin | 5-15ms intra-DC | 1% (cold IDs only) |

The 95/4/1 split is **Pareto's law applied to URL traffic**. A small set of viral URLs dominates QPS; demand-driven cache fill naturally places hot URLs at every edge POP.

**2. Walk it concretely.**

A new URL `srt.ly/aB3xK9z` is created at T+0. Twitter shares it. Within 30 min:

```
T+0      First user (us-east) requests /aB3xK9z:
         → CDN POP us-east — MISS (URL is fresh)
         → forwards to origin (us-east region API)
         → API checks Redis — MISS (cold key)
         → API hits DB shard — INSERT happened ~30s ago — HIT, returns long_url
         → API responds 301 + Cache-Control: max-age=31536000
         → CDN POP us-east caches the response
         → API writes to Redis on the way back (write-through populate)

T+10s    Second user (us-east, different city) → CDN POP us-east — HIT — 8ms response

T+1m     User in eu-west → CDN POP eu-west — MISS (different POP)
         → forwards to origin (us-east) — cross-Atlantic ~80ms RTT
         → Origin Redis — HIT — 1ms
         → 301 returned; CDN POP eu-west caches it
         → eu-west users from now on get 5-15ms

T+30m    URL has propagated to all 200 POPs.
         CDN hit rate at edge → ~99%
         Origin sees <1% of total traffic
         Redis hit rate (conditional on origin-traffic) → ~95%
         DB sees ~0.05% of total
```

The conditional arithmetic matters in interviews: of 100 requests, CDN serves 95 and forwards 5 to origin; of those 5, Redis serves 4 and forwards 1 to DB. So Redis hit rate **conditional on origin-traffic = 80%; unconditional = 4%**. Candidates routinely confuse the two.

**3. The cost you're accepting.**

| Property gained | Cost paid |
|---|---|
| p99 < 100ms (CDN-served are <20ms) | Cache invalidation is hard — 200 POPs × ≥5min TTL = stale URL served for ~5 min after takedown |
| Reduces DB load ~100× (1% of original) | Redis sized for ~9 TB hot working set → ~$10k/mo |
| Geographic locality (US user → US POP) | CDN egress at scale → ~$5k/mo at 300k QPS peak |
| CDN handles read DDoS naturally | Read-after-write delay — new short URLs have ~30s edge-warmup before they're geographically fast everywhere |

The painful trade-off is **stale URLs after takedown**. If a malicious URL is reported, the edge cache holds it for up to the TTL. Mitigations: short TTL (e.g. 1h instead of 1y for high-risk URLs) + active CDN purge API call on takedown + DB-side `deleted` flag so cold reads return 410 Gone.

**4. Failure modes the interviewer will drill into.**

| Failure | What goes wrong | Mitigation |
|---|---|---|
| Single Redis instance failure | 4% of requests fall through to DB; DB sees 4× normal load briefly | Redis Sentinel for auto-failover; cluster mode with RF=2 |
| Hot key — one URL goes viral, lands on one Redis shard at 100k QPS | Single Redis node CPU saturates → tail latency spike → cascade to API tier timeouts | (a) Replicate hot keys across shards via promotion; (b) per-pod LRU L1.5 cache in front of Redis; (c) CDN should absorb this anyway — if it doesn't, the URL is *new* and edge hasn't warmed |
| CDN POP cold start (new POP added) | New POP serves 100% misses to origin for hours | Pre-warm: at deploy, replay top-1M URLs through new POP from a synthetic-load job |
| Cache stampede on hot URL expiry | All POPs simultaneously refetch when TTL expires → origin spike | Jitter TTLs (TTL × random(0.8, 1.2)); or use stale-while-revalidate semantics (serve stale + async refresh) |
| Stale URL after takedown | User gets redirected to URL we know is malicious | Short TTL on high-risk URLs + active CDN purge API + DB soft-delete returns 410 Gone on cold reads |

**5. How to derive it in an interview from first principles.**

1. State the constraint: p99 < 100ms over network → can't hit the DB every request (DB I/O + RTT alone exceeds budget for cross-region users).
2. Workload: 100:1 reads:writes; reads are point-lookups by ID; URLs are immutable post-creation.
3. **Immutable + high read ratio = cacheable.** Caching tier is mandatory.
4. Where to cache: closest to user (CDN edge) handles geographic latency for the 95% Pareto on hot URLs.
5. CDN misses (cold or evicted URLs) still need <100ms → second tier (Redis intra-DC) catches them.
6. Redis misses → DB. DB is sharded anyway (write throughput), so cold reads distribute evenly across shards.
7. Cache invalidation is the price — for URL shortener, soft eventual consistency on takedown is acceptable (a stale redirect is a soft failure unless the URL was redirected away from phishing — which is why high-risk URLs get short TTLs + active purge).
8. You've derived a 3-tier cache. Each tier exists because the one above can't satisfy a specific constraint alone (geo, intra-DC latency, persistence).

**6. Where this shows up in production.**

- **bit.ly**: 3-tier topology — Akamai CDN at edge + Membase-derived Couchbase L2 + Cassandra primary. 2012 "10 billion clicks" engineering post cited ~95% edge hit / ~80% L2 hit rates.
- **Cloudflare R2**: 3-tier — edge cache at 285+ POPs + regional cache + origin object store. "Zero egress fees" was made economically viable by the 90%+ edge hit rate; egress to other clouds would otherwise cost ~$0.09/GB.
- **Wikipedia (MediaWiki + Varnish)**: 4-tier — Varnish at edge POPs + application cache + memcached + MariaDB. Wikimedia engineering posts cite ~95% Varnish hit / ~3% memcached / ~2% MariaDB on Article reads.
- **Netflix EVCache**: Multi-region cache layer in front of Cassandra. 30+ trillion ops/day at peak. Multi-region replication is a *stream of invalidations via Kafka*, not a replicated store — same trade-off pattern.
- **YouTube watch-page metadata**: Edge cache for `/watch?v=X` metadata; Bigtable as origin. Documented in Google SRE Book Ch.27 — they explicitly call out the 95% edge-hit assumption as load-bearing for capacity planning.

### Bottlenecks + scaling levers

| Scale point | First bottleneck | Lever |
|---|---|---|
| 10× reads (3M QPS peak) | CDN POP cache capacity per region during viral spikes | Pre-warm hot URLs across all POPs at write time |
| 100× reads (30M QPS peak) | Origin API tier on the residual CDN-miss traffic | Add L1.5 cache (per-pod LRU) in front of Redis; targets repeat misses |
| 10× writes (12k QPS peak) | Counter-row contention per shard | Counter pre-allocation — each pod reserves 1k IDs at a time (cuts contention 1000×) |
| 10× storage (~1.8 PB) | Shard count for write throughput | Add shards; rehash using doubling with incremental rebalance |

### Trade-off matrix

| Option | Latency | Cost | Complexity | Consistency |
|---|---|---|---|---|
| Single DB, no cache | ❌ | ✅ | ✅ | ✅ |
| Single Redis cache, no CDN | ⚠️ (network RTT dominates) | ⚠️ | ⚠️ | ⚠️ |
| **3-tier CDN + Redis + sharded DB (chosen)** | ✅ | ❌ | ❌ | ⚠️ (eventual on edge invalidation) |
| CDN-only (edge as primary store) | ✅ | ✅ | ❌ | ❌ (no durability story) |

Chose 3-tier for the **latency/cost balance** within the durability constraint. The eventual-consistency window on invalidation (~5 min worst case) is acceptable for URL shortener — a stale redirect is a soft failure, *unless* the URL was redirected away from a phishing target, which is why high-risk URLs get short TTLs + active CDN purge.

### Common follow-ups

1. **Custom aliases (`/my-vacation-pics`)** — Add a `custom_aliases` table with UNIQUE constraint on the alias string. Check-before-insert on the write path; the redirect path doesn't change (alias and counter-generated IDs share the lookup table). Cost: write latency rises ~5ms for the uniqueness check.
2. **Analytics on clicks** — Must be off-hot-path. Redirect handler fires-and-forgets a click event to Kafka; downstream pipeline aggregates offline (hourly rollups). The redirect itself adds **0ms** for analytics.
3. **Abuse / phishing URLs** — Async scan at write time + maintain a deny-list cache at the CDN tier (Cloudflare Workers can do this). Block-scan latency ~100ms is hidden behind a "verifying URL" UX before the short URL is returned.
4. **URL deletion / takedown** — Mark `deleted=true` in DB; issue CDN purge for that path; Redis `DEL`. Edge POPs without active purge fall back to TTL expiry — bounded window ~5 min. Cold reads hit DB and return 410 Gone.
5. **Multi-region** — Counter ranges become region-prefixed (`us:counter`, `eu:counter`) — non-overlapping by construction. CDN POPs are naturally local. DB cross-region replication is async leader → follower; clients in the secondary region read from the local replica with bounded staleness.

### What top-tier looks for

- **Mid-tier says**: "Use a hash of the URL. Cache in Redis. Sharded DB."
- **Staff-tier says**: "Hash collides at scale — birthday paradox kicks in at 7-char base62 around 100K collisions/day; retry breaks predictable insert latency. So: sharded counter + base62, pre-allocated in 1k blocks per pod to kill counter-row contention. For reads, the 95/4/1 Pareto split decides the cache topology: CDN for the 95%, Redis for the 4% (with consistent hashing + replicated hot keys), DB for the 1%. The interesting failure mode isn't capacity — it's stale-after-takedown, which is why high-risk URLs get short TTLs + active CDN purge."

The difference: mid-tier names patterns. Staff-tier names the **failure mode that decides each pattern** (birthday paradox decides counter; Pareto decides cache topology; takedown decides invalidation strategy), then derives.

### Diagnostic questions (self-quiz)

1. **Why not just hash the URL for the short ID?** — wrong: "MD5 is fast and deterministic." Right: at 7-char base62 (62⁷ = 3.5T slots), 100M new URLs/day puts collision rate ~1 per 30 days (birthday paradox at √N collision threshold ≈ 1.86M). Retry-on-collision breaks idempotent insert semantics.
2. **What's your cache invalidation strategy when a URL is taken down?** — wrong: "Short TTL." Right: TTL + active purge to CDN (e.g. Cloudflare's `/purge` API) + Redis `DEL` + DB soft-delete returning 410 on cold reads. Window bounded by CDN propagation (~30s typical).
3. **Why is the redirect cacheable but the shortening request isn't?** — wrong: "Reads are cacheable." Right: the redirect response is a *pure function* of the short ID (immutable post-creation); the shortening request creates new state, and a "cached" response would mean returning a previously-allocated ID for a new URL — which is incorrect.
4. **At 10× scale (30M QPS peak redirects), what fails first?** — wrong: "The DB." Right: the DB is already off the hot path. What fails first is CDN POP cache capacity in a single region during a hot-URL spike (viral link in one geography). Mitigation: pre-warm to all POPs at write time + cross-POP origin cache for warm-cold transitions.
5. **Why base62 and not base64 (URL-safe variant)?** — wrong: "Looks cleaner." Right: standard base64 includes `+` and `/`, both URL-unsafe per RFC 3986 (require percent-encoding). Base64url is fine but uses `-` and `_`, which look less like a "premium" short URL. Base62 (`a-zA-Z0-9`) is URL-safe with zero escaping needed.
